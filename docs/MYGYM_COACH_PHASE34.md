# myGym 教练优化：长期记忆与候选动作筛选

## 使用方法

打开教练页面右上角的“更多”菜单，选择“教练记忆”。

- 长期训练备注：填写希望每次咨询都能参考的情况，例如固定训练时间。最多 1200 字符。
- 偏好的动作 / 希望避开的动作：输入中文、英文名称或动作 ID 搜索，再添加到相应列表。每类最多 20 个；选择另一类会移出原列表。
- 点击“保存”后生效。取消或关闭不会保存；清空也必须点击“保存”才生效。

已有问卷里的目标、经验、器械、限制、喜欢与不喜欢的描述继续保留。记忆不是自动聊天摘要：模型不会根据一句临时抱怨永久修改偏好，也不能通过回复写入这些字段。

## 阶段 3：可控的长期个性化记忆

新增字段位于现有 `S.coach.profile`：`memory`、`preferredExerciseIds`、`avoidedExerciseIds`，沿用个人资料的保存、备份和配对同步。旧数据缺少字段时按空值读取，无需迁移训练记录。

创建计划、训练问答、审查和复盘使用同一个有界白名单清理函数。记忆随每次请求发送给所选供应商；编辑页明确提示不要输入密码或 API 密钥。清理器不会读取凭据、其他个人资料或任意嵌套字段。

清空仅影响后续请求，不删除此前的聊天、在途请求或供应商已接收的记录。已运行任务使用请求开始时的上下文。记忆变化不会自动生成、应用或撤销计划。

## 阶段 4：候选动作优先级

保留原有器械过滤、身体部位加权轮选、常见动作基础顺序，以及计划/训练历史动作优先保留规则。在此基础上：

1. 显式偏好动作在部位候选中优先，并尽量在原有候选预算内保留。
2. 希望避开和已隐藏的动作不进入普通候选。
3. 计划或历史中的这些动作仍作为上下文保留，标记 `contextOnly`；器械不匹配的保留项另标记 `equipmentUnavailable`。
4. 候选携带器械、目标肌肉和偏好/已练标记，让模型说明选择依据。自建动作没有可验证的器械信息，提示词要求先询问。
5. 新计划以及审查中的新增/替换动作若选择了明确避开的 ID，共用流水线会拒绝并最多修复一次。已有动作的解释、移除和参数调整不因此被一概阻断。

器械过滤不会因没有匹配项而退回整个动作库；徒手动作仍按原规则可用。候选规模沿用创建最多 160、审查/问答最多 60 的基础预算；原有历史保留项及自建动作可能使总数超出基础预算，此次未重写这一行为。

偏好排序是确定性规则，不是新的训练效果预测模型。目标、经验、时长和限制继续由模型结合问卷与记录判断；没有从伤痛描述自动推断医疗禁忌。自由文本回答不能像结构化计划一样逐个校验动作，仍需用户判断。

## 实现依据

| 范围 | 文件 |

| 字段白名单、长度与冲突处理 | `api/coach/core/memory.js` |

## 验证与限制

- 核心及服务端相关回归：126 项通过，覆盖边界、隐私白名单、候选确定性、器械与避开条件、严格计划校验、原有问答及接口契约。
- 前端相关回归：10 个文件，285 项通过，覆盖编辑取消、确认清空、原有聊天与提案、本地流水线、两端规则一致性和现有持久化逻辑。
- 网页版与移动版前端生产构建均通过，产物放在仓库外的本地验证目录；移动版标识、资源完整性及服务工作线程盖章检查通过。
- 独立浏览器验证真实移动版界面与本地流水线：中文搜索、偏好保存、刷新持久化、请求携带记忆、取消与确认清空，以及待确认提案保留。供应商响应为模拟，未使用真实密钥。
- 提示词/动作数据和静态 API 文档生成一致性检查通过。
- `payload-bounds` 两处旧训练样例已超出审查窗口，提交前版本同样无法在窗口中找到记录；仅更新这两项测试的样例日期，未改变业务窗口。

没有使用真实供应商密钥评价模型回答质量，没有重新打包 APK 或进行真机验收。构建仍提示项目已有的大分包和动态导入警告。已安装 APK 和已部署网站不会因本地源码改变而自动更新，服务器配对模式也需要更新后端。

本阶段不包含自动提取/确认聊天记忆、无限对话历史、医学动作匹配或模型效果保证。未执行 Git 提交或推送。
